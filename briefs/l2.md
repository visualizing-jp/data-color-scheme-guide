## 背景
リポジトリ visualizing-jp/data-color-scheme-guide は、初学者向けの日本語スクロール型解説ページ「データの性質に合ったカラースキームの選び方」です。講義スライド「データの性質を表現する色の考え方」をもとに、「色相は種類の違いを、明るさ（明度）は量の大小を伝える」という一本の筋で、色が見えるしくみ → 色の3つのつまみ → データの性質とカラースキーム（定性的・連続的・分岐的）→ 色覚の多様性への配慮 → まとめ、の順に説明します。読者は、色彩やデータ可視化を学び始めたばかりの学生・社会人です。

ビルド工程のない静的サイト（バニラJSのESモジュール、D3 v7 を同梱）で、図・共有モジュール・本文を、担当ごとに互いのファイルに触れずに並行して作っています。最初に `README.md` を読んでください。図の契約、担当範囲、共通の操作部品、動かし方が書いてあります。

あなたの作業ブランチは `w1/l2-palettes`（`s0/skeleton` から分岐）です。

- Okabe–Ito（ID は `OkabeIto`、種別は定性的、`source` は `'okabe-ito'`）。色の順は「オレンジ、スカイブルー、青みがかった緑、黄、青、朱、赤紫、黒」。`get('OkabeIto', n)` は先頭から n 色（n は 2〜8）。色覚安全フラグは全階級で真。

データは `lib/palettes.js` の中に定数として埋め込みます（実行時に外部から取得しません）。ColorBrewer のデータは、下の「調査結果」の手順で原典のファイルから機械的に変換して作ります。原典に接続できない場合は、D3 を使って同じ値を取り出せます（リポジトリに同梱の `vendor/d3/d3.min.js` に `d3.schemeBlues[5]` などの形で入っています）が、色覚安全フラグは調査結果の一覧表から起こします。

`DEFAULTS` は `{ qualitative: 'Set2', qualitativeSafe: 'OkabeIto', sequential: 'Blues', diverging: 'RdBu' }` です。`ATTRIBUTION` と、ファイル冒頭の帰属表示のコメントは、調査結果の文面案を使います。

`scale(id, n, domain, { center })` は JSDoc のとおり等間隔で区切ります。境界ちょうどの値は上の階級に入れ、domain の外の値は端の階級に入れます。

## 0. 要点

- 色データは `colorbrewer_schemes.js` の1ファイルで全35パレット・265（パレット×階級数）が揃い、色覚フラグも同じファイルにある。変換スクリプトは実行済み。
- 色覚フラグは「値1のみ true」と決める。`blind` 配列は長さ1なら全階級に適用、長さ2以上なら `blind[階級数-3]`（ColorBrewer公式サイトのJSの規則）。
- **ColorBrewer の定性的パレットは、8階級で色覚安全なものが1つもない**（Set2・Dark2 は3階級のみ安全）。8色が必要な定性的パレットの既定は Okabe–Ito を推奨する。
- Okabe–Ito の8色RGBは、Wong (2011) Nature Methods の Figure 2 と、Okabe & Ito 本人のページの画像の両方に数値が載っており、2つが一致した。

## 1. colorbrewer_schemes.js の生URLと構造

- 生ファイルURL【実行確認】：`https://raw.githubusercontent.com/axismaps/colorbrewer/master/colorbrewer_schemes.js`（200、38,526バイト、sha256 `52e6a6edbbe4bbb95467cb84fb7db8fcbb1d6d219c975851c4c9d79334f00a41`、2026-11-23取得）。
  - ルート直下にある。`/export/colorbrewer_schemes.js` は404。
  - `https://colorbrewer2.org/colorbrewer_schemes.js` も同一内容（バイト一致）【実行確認】。
- 構造【実行確認】：`var colorbrewer = { Spectral: {3: [...], 4: [...], ..., 'properties': {...} }, ... };`。JSON ではなく JS で、キー引用符が不揃い、文字列は単引用符、コメント `/*** Diverging ***/` を含む。そのため `JSON.parse` は使えず、Node の `vm` で評価する。色は `'rgb(222,235,247)'` 形式。
- `properties` の中身【実行確認】：
  - `type`：`'qual'`（定性的）、`'seq'`（連続的）、`'div'`（分岐的）。
  - `blind`、`print`、`copy`、`screen`：整数の配列。
- 階級数の範囲【実行確認】：定性的は Set2/Accent/Dark2/Pastel2 が3〜8、Set1/Pastel1 が3〜9、Set3/Paired が3〜12。連続的は全18種が3〜9。分岐的は全9種が3〜11。階級数の欠番はない。
- 配列の意味と値の意味：公式の説明は2か所を閲覧して確認した。
  - 値の意味（公式サイトのJS `https://colorbrewer2.org/colorbrewer.js`、関数 `getWord`）【閲覧確認】：`1` ＝ 問題なし（アイコン緑、表示は "color blind friendly"）、`2` ＝ 「possibly not」（アイコン maybe、要確認）、`0` ＝ 「not」（アイコン bad、避ける）。絞り込みチェックボックスは値が `1` のものだけを残す（`!= 1` を除外）。
  - 階級数との対応（同JSの `checkColorblind` など）【閲覧確認】：`properties.blind.length > 1 ? properties.blind[numClasses-3] : properties.blind[0]`。つまり長さ1の配列は、そのパレットの全階級数に同じ値を適用する。長さ2以上なら添字は「階級数 − 3」（添字0 ＝ 3階級）。
  - 4つの配列の意味（公式の説明 `https://colorbrewer2.org/learnmore/usability.html`、サイト上のアイコン解説）【閲覧確認】：
    - `blind` ＝ 赤緑色覚異常の人が混同しない（Color Blind Friendly）。
    - `print` ＝ カラー印刷向き。
    - `copy` ＝ 白黒コピーで明度差が保たれる（分岐的は不可と明記、実データでも `[0]`が多い）。
    - `screen` ＝ ノートPCのLCDで色が飛びにくい。
    - アイコン「?」＝ potentially an issue (might be ok - check first)。「×」＝ very likely an issue (best avoided)。
- 公式の注意【閲覧確認】：同ページに「赤緑色覚異常は男性の約8%、女性の約0.4%。重さは様々なので、一部の人には問題になりうる『?』を付けたスキームがある」とある。
- 配列の長さが足りない例外【実行確認】：`Paired` の `blind` は長さ9だが階級数は3〜12の10個。12階級に対応する値がない（`undefined`）。公式JSの規則だと `!f` が真になり「not」扱いで、絞り込みでも除外される。変換では `=== 1` で判定するので自然に `false` になる。
- 同じ色の別形式【実行確認】：D3向けの HEX 版 `https://raw.githubusercontent.com/axismaps/colorbrewer/master/export/colorbrewer.js`（35パレット、HEX、色覚フラグなし）。265個すべての色が上のファイルの変換結果と一致した（差異0）。`export/colorbrewer.json` は rgb() 形式で `properties` を含まない。つまり**色覚フラグは `colorbrewer_schemes.js` にしかない**。

## 2. 変換スクリプト（実行済み）

Node.js 22。`node convert.mjs colorbrewer_schemes.js > palettes.json` で、確定済みのデータ形の配列（35要素）が出る。種別名は `qual→qualitative`、`seq→sequential`、`div→diverging` に写す。`classes` と `colorblindSafe` のキーは階級数（JSONでは文字列になる）。`_blindRaw` は検証用なので、実装では捨てる。

`vm` は取得ファイルの JS を評価するため、信頼できない入力には向かない。sha256 で固定した上で、生成結果の `palettes.js` をリポジトリに入れ、実行時には評価しない運用を勧める。

```js
// Usage: node convert.mjs colorbrewer_schemes.js > palettes.json
// colorbrewer_schemes.js は `var colorbrewer = {...}` 形式。vm で評価して取り出す。
import fs from 'node:fs';
import vm from 'node:vm';
const src = fs.readFileSync(process.argv[2], 'utf8');
const ctx = {};
vm.createContext(ctx);
vm.runInContext(src, ctx);               // var colorbrewer が ctx.colorbrewer に入る
const cb = ctx.colorbrewer;
const TYPE = { qual: 'qualitative', seq: 'sequential', div: 'diverging' };
const hex = (s) => {
  const m = /^rgb\((\d+),\s*(\d+),\s*(\d+)\)$/.exec(s);
  if (!m) throw new Error('bad color ' + s);
  return '#' + m.slice(1).map(n => Number(n).toString(16).padStart(2, '0')).join('');
};
const out = [];
for (const [id, scheme] of Object.entries(cb)) {
  const { properties } = scheme;
  const classes = {}, colorblindSafe = {};
  for (const [k, v] of Object.entries(scheme)) {
    if (k === 'properties') continue;
    const n = Number(k);
    classes[n] = v.map(hex);
    if (classes[n].length !== n) throw new Error(`${id}/${n} length`);
    // colorbrewer.js (checkColorblind) と同じ規則: 配列長>1 なら [n-3]、長さ1なら [0] を全階級に適用。
    const b = properties.blind;
    const flag = b.length > 1 ? b[n - 3] : b[0];
    colorblindSafe[n] = flag === 1;        // 1 のみ true。0=不可, 2=要注意(maybe) は false
  }
  out.push({ id, type: TYPE[properties.type], source: 'colorbrewer', classes, colorblindSafe,
             _blindRaw: properties.blind }); // 検証用。実装では捨ててよい
}
process.stdout.write(JSON.stringify(out, null, 1));
```

実行結果【実行確認】：35パレット、色265組（`classes` の全キーの合計）、`classes[n].length === n` の検査を全件通過。

## 6. 種別ごとの既定パレットの推奨

指標は、基本情報の条件（定性的は8色必要、連続的・分岐的は5〜9階級、色覚フラグ）に、私が `palettes.json` から計算した明度（CIE L*）と白背景に対するコントラスト比を加えた【実行確認、計算は自作の `analyze.mjs`】。

| 種別 | 推奨 | 理由 |
|---|---|---|
| 定性的 | **Okabe–Ito（8色）**。ColorBrewer だけで揃えるなら `Dark2` の8階級（フォールバック） | ColorBrewer の定性的パレットで8階級が色覚安全なものはない（§4）。Set2・Dark2 は8階級で `blind=0`。Okabe–Ito は色覚多様性を考慮して作られた8色（黒を含む）。Dark2 は Set2 より白背景で見やすい（8色のうち7色が3:1前後以上、最低は黄 `#e6ab02` の2.06。Set2 は全色が約2.6以下で `#ffd92f` は1.38、`#a6d854` は1.67）。 |
| 連続的 | **Blues**（5〜9階級） | 3〜9階級すべて色覚安全（`blind=[1]`）。単色相で、明度が単調に下がる（5階級：96→35、7階級：96→31、9階級：98→21）。初学者に説明しやすい。次点は YlGnBu（多色相で段差が見分けやすく、これも全階級 true、L* 99→13）。 |
| 分岐的 | **RdBu**（5・7・9階級など奇数） | 3〜11階級すべて色覚安全（`blind=[1]`）。中央が `#f7f7f7`（L* 97）で両端が暗く、明度が中心から対称に下がる（7階級：38 68 90 97 90 66 42）。奇数階級のときだけ中立色の中央がある（偶数は中央の色がなく、ページでは奇数を既定にする）。次点は PuOr、BrBG（どちらも全階級 true）。Spectral と RdYlGn は色覚フラグが悪いので既定にしない。 |

- RdBu の中央色 `#f7f7f7` は白背景の点・棒ではほぼ見えない。ページの背景を白にするなら、中央は枠線を付ける、背景を薄灰にするなどの配慮が必要。
- Okabe–Ito の黒は定性的な系列として使えるが、黄 `#f0e442` は白背景でコントラスト比1.32と低い（`#e69f00` 2.25、`#56b4e9` 2.31）。線や小さな点に使うなら、黄とオレンジ・空色は白背景を避けるか、形や線種の違いと併用する。
- Okabe–Ito を使う場合、データ形は `source: 'okabe-ito'`、`classes: { 8: [...] }`（または黒を除いた7色と合わせて 7・8）、`colorblindSafe: { 8: true }` とするのが自然。この `colorblindSafe: true` は、Okabe–Ito（および Wong）が色覚多様性に配慮した配色として提案したことに基づく。ColorBrewer のフラグのような階級数ごとの検証値ではない。
- 色覚の保証は「色だけに頼らない」こと（凡例の直接ラベル、マーカー形状、線種）と併用して初めて成り立つ、という説明をページに入れるとよい（Okabe & Ito の redundant coding の項と同趣旨）。
